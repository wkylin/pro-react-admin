# RBAC、资源范围与独立审批

## 参考项目与本项目的取舍

参考项目：[rbac-access 源码](https://github.com/wkylin/rbac-access)和[在线演示](https://wkylin.github.io/rbac-access/)。它在浏览器本地展示员工、角色、权限项、资源范围、变更预览、独立审批、审计和 TOTP。其状态保存在 `localStorage`，适合学习交互流程；浏览器内的审批和密码复核不能作为服务端安全控制。

Pro React Admin 已有租户账号、角色、路由策略、权限快照、用户与角色管理、SQLite 事务及审计，因此本实现沿用这些实体，没有复制另一套账号表或权限项目录。RBAC 变更集中处理角色授权、用户与角色记录范围、访问变更审批；后续的企业登录验证器按[独立的 TOTP 指南](../operations/ENTERPRISE.md#企业账号登录验证器-totp)接入现有 principal。资源范围当前只覆盖组织管理的 `user` 与 `role` 记录，不声明支持参考项目中的金额、有效期等业务条件。

| 关注点     | Pro React Admin 的实现                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 身份       | 企业模式使用现有租户会话、principal、组织成员和单个组织角色；演示模式使用测试账号。                                                   |
| 权限       | `resource:action`、`resource:*`、`*:*`，授予与资源范围必须来自同一角色。导航、按钮、权限检查器和 API 使用同一授权语义。               |
| 资源范围   | 每个角色可为 `user`、`role` 分别设 `global`、`restricted`（指定记录 ID）或 `deny`。旧角色未配置时视为 `global`，保持迁移前授权。      |
| 审批       | 角色权限/范围、成员角色/重新启用先预览，再提交原因，独立审批人批准后才在事务中应用。申请冻结前后状态、受影响成员摘要和 SHA-256 指纹。 |
| 审计与实时 | 提交、批准、拒绝和失效写入服务端审计；审批列表通过租户范围的 WebSocket 失效通知刷新。                                                 |

平台租户管理独立于租户内 RBAC：只有运维显式授予的 `platform-admin` principal 可访问所有租户；`tenant-admin` 的 `*:*` 不包含 `tenant:*`。角色授权编辑器在“权限管理”菜单复用，不允许通过普通租户角色提升平台身份。使用方式见[平台租户与权限管理](../operations/ENTERPRISE.md#平台租户与权限管理)。

## 如何使用

### 公开演示

1. 在演示登录页选择 `admin@test.com`，进入**组织管理 → 角色管理**。
2. 编辑普通角色的权限或用户/角色记录范围，保存后核对预览和受影响成员，填写申请原因并提交。
3. 保持同一个页面会话，切换到 `reviewer@test.com`，打开**组织管理 → 访问审批**，查看变更前后和资源范围，填写审批意见后批准或驳回。
4. 回到管理员账号，可在**权限示例**查看当前登录身份的授权、范围和菜单判定。演示审批数据只在当前运行中的页面内存里保存；刷新会清空。演示角色编辑也不会修改固定测试账号的登录授权。

演示流程和企业 API 使用相同的页面，但演示数据、审核和审计均在浏览器内，不能代替真实租户的安全控制。

### 企业账号

按[企业资源指南](../operations/ENTERPRISE.md#启动真实业务模式)启动单实例 API 和持久化 SQLite，使用租户 ID、邮箱和密码登录。已有 `tenant-admin` 可以创建成员、角色。至少创建一个**独立的活跃审批人**，其角色拥有 `access:read` 与 `access:approve`；审批人不能是申请人、被变更的成员，也不能属于正在变更的角色。操作员还需要对应的 `role:update` 或 `user:update`，并且只能授予自身已有的权限和资源范围。

存在独立审批人时，新角色先以空权限创建，再编辑其权限/范围提交审批；带授权的成员先以停用状态创建，再申请启用。表单执行这两步，并在创建后的预览中显示具体目标与影响；取消预览会保留空角色或停用成员，可再次编辑。名称、邮箱、密码等非访问字段依现有规则直接保存。停用和删除沿用现有受保护规则，最后的有效管理员和审批能力不能被移除。

`restricted` 列表只返回允许的 ID，读取或修改范围外的单条记录返回 403。菜单可显示有受限列表访问的页面，进入页面后只看到范围内的记录；`deny` 会隐藏相应页面。服务端每次请求重新读取角色，不相信页面按钮的显示状态。审批时重新校验申请人授权、目标状态和受影响成员集合；变化后申请标为 `stale`，不会应用旧方案。拒绝只更新申请和审计。

### API 契约

| 方法 | 路径                                      | 用途                                                              |
| ---- | ----------------------------------------- | ----------------------------------------------------------------- |
| GET  | `/api/admin/access-governance`            | 检查是否已有独立审批人。                                          |
| POST | `/api/admin/access-requests/preview`      | 提交 `{kind,targetId,change}`，返回前后状态、受影响摘要和指纹。   |
| POST | `/api/admin/access-requests`              | 在预览结果上增加 `reason` 和 `fingerprint` 创建待审申请。         |
| GET  | `/api/admin/access-requests`              | `access:read` 查看本租户申请；支持 `page`、`pageSize`、`status`。 |
| POST | `/api/admin/access-requests/:id/decision` | `access:approve` 提交决定（approve 或 reject）与原因。            |

`role` 的 `change` 只包含 `permissions`、`scopes`；`user` 的 `change` 只包含 `role`、`status`。客户端预览不授权批准：API 在事务里重新认证申请人和审批人、核对影响指纹并应用变更。`approval_required`（HTTP 409）表示有独立审批人时不能绕过流程直接修改访问字段。申请和资源范围由 schema v3 保存；旧库需要按[SQLite 迁移流程](../operations/ENTERPRISE.md#sqlite-迁移备份与恢复)离线升级并先验证备份。

权限代码与范围的纯函数在 [`accessDecision.ts`](../../src/platform/auth/model/accessDecision.ts)，服务端校验在 [`service.mts`](../../api/enterprise/service.mts)，路由/菜单声明在 [`route-policy.json`](../../config/route-policy.json)。该共享函数只统一授权判定规则；可信身份、租户范围、事务和审计仍由企业 API 执行。
