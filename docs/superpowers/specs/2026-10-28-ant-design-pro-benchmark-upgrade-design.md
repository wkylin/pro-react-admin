# Ant Design Pro 对标升级设计

- 日期：2026-10-28
- 状态：2026-10-28 已批准，第一批已实施并验证
- 目标：保留现有 React、Ant Design、路由、模块和企业 API 架构，增量提升页面模板与开发文档的可用性。

## 意图与依据

本项目要成为团队能直接开始开发管理应用的工作区。使用者应能快速找到常见页面模式，运行一个完整示例，知道如何接入真实 API、登记菜单和权限，并验证交付结果。用户指定以 Ant Design Pro 的功能和文档体验为主要标杆，选择保留现有架构、增量补齐。

以下是 2026-10-28 通过 Tavily CLI 检索并核对的官方 GitHub 仓库快照；比较的是可学习的结构和体验，不按 Star 数量评价质量，也不把商业扩展算作开源实现。

本项目已有租户隔离、服务端 RBAC、访问审批、审计、模块 v2 契约、质量门禁和 PostgreSQL 企业 API；这些不应为了对标而重写。现有 [企业模块清单](../../../src/projects/enterprise/modules.ts)只装配 administration，[默认模块清单](../../../src/app/modules/default.ts)装配 administration 与 notifications。现有 [文档索引](../../README.md)仍把真实企业 API 主要描述为单实例 SQLite，而 [Vercel + Neon 指南](../../deployment/VERCEL_NEON_ENTERPRISE.md)已记录独立 PostgreSQL 路径。`check:docs` 能检查链接、锚点、命令，不能判断这些描述是否同步。后端 [PostgreSQL 测试](../../../server/enterprise/postgres.test.mjs)使用 PGlite；目标数据库的部署验收另行记录，不能用模拟引擎测试代替。

## 目标与验收

1. 新读者从 README 在两次跳转内找到“页面模板目录”和“创建一个业务模块”的步骤，文档中的命令可直接运行。
2. 展示应用与企业入口都默认提供一条连贯的示例资源流程：查询列表 → 创建（基础表单或分步表单）→ 详情 → 结果反馈。页面不是孤立截图；创建结果在当前演示会话内可从列表与详情读取。
3. 每个模板页面标出适用场景、源码、数据边界、路由/菜单/权限入口、替换为真实 API 的位置和验证命令。演示数据明确标注为演示，不承诺生产持久化或服务端授权。
4. 两个入口的路由、菜单、权限、翻译和示例模块装配通过现有契约门禁；Webpack 与 Vite 均能构建。两个入口各有一条浏览器用例验证模板可见性，至少一条用例验证从创建到详情的完整流程，领域数据逻辑有针对性的单元测试。
5. 文档导航同时说明本地 SQLite 演示、自托管 SQLite 和独立 Vercel + PostgreSQL 三条真实边界，并链接现有生产验收记录。修正文档后运行 `pnpm run check:docs`。

## 非目标与约束

- 本轮不迁移 Umi Max、Refine 或 Backstage，不替换当前应用壳、授权服务、双构建器和组件包。
- 页面模板是工作区示例，不新增公开生产业务 API、数据库表、OIDC 或动态第三方插件加载。
- 不把页面模板的内存数据或展示应用的 Mock 权限当成服务端授权，不把仓库测试通过当成线上验收完成。企业入口明确把模板标为“示例”，真实用户、租户、审计和访问审批仍来自服务端。
- 新业务页面使用 `src/features/<name>`、模块契约 v2、两份现有 route-policy 和 i18n；遵守导入边界。模板默认进入展示和企业入口，但通过懒加载及独立 Provider 隔离演示代码与真实企业数据。
- 第一批模板按 Ant Design Pro 的常用管理页模式设计，但使用本项目的 Ant Design 6 与现有组件。是否引入额外 ProComponents 包由实现时的明确收益决定。

## 方案选择

| 方案                           | 收益                                                         | 代价                                                       | 结论       |
| ------------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------- | ---------- |
| 保留架构，补齐模板和任务式文档 | 能沿用现有租户/权限/模块/构建与 CI，并直接改善“开箱可用”体验 | 需要自行维护模板与文档                                     | 用户已选定 |
| 整体迁入 Umi Max/ProComponents | 与 Ant Design Pro 的实现更接近                               | 路由、状态、构建、微前端和脚手架均需迁移，难以隔离回归风险 | 本轮不采用 |
| 先抽成 Refine 式通用框架       | 长期可形成独立框架产品                                       | 先重写平台层，短期仍缺少可用页面和文档                     | 本轮不采用 |

## 实施形态

第一批建立“业务页面模板”模块，以同一组演示申请记录贯穿查询表格、基础表单、分步表单、详情和提交结果。演示 Provider 在模块实例内保存数据，保持与身份/应用根的生命周期一致；表单有字段校验、提交失败与成功状态，列表有查询、筛选、分页和空状态，详情能显示刚创建的记录。模块同时进入 default 与 enterprise 的模块清单，页面懒加载；两份 route-policy 都登记菜单和精确路径，并用已有的 `home:read` 授权点限制在有效会话内，不为演示模板新增服务端业务权限。企业入口的菜单、页头和提交结果均显式标注“示例数据，当前会话有效”；不调用企业业务 API，不写真实审计。文档再说明如何把同样的页面模式接到真实业务 Provider 与专属服务端权限。

第一批同时调整 README 与 `docs/README.md` 的入口顺序，增加一篇按任务导航的模板指南：从运行模板、读源码、增加字段、替换数据 Provider、配置权限，到运行验证命令。修正 `docs/architecture/ENGINEERING_OVERVIEW.md`、`docs/architecture/ARCHITECTURE.md` 与相关索引中对 PostgreSQL 企业 API 的遗漏或过时表述；保留 SQLite 单实例方案的准确适用范围。

后续批次按实际使用反馈增加高级表单、卡片列表、账户设置和更完整的 Dashboard 模板；再考虑 OpenAPI 契约/客户端生成、真实 PostgreSQL CI 集成、SQLite/PostgreSQL 行为一致性测试、根 TypeScript strict 迁移和文档版本化。这些是独立里程碑，不阻塞第一批交付，也不宣称已经实现。

## 交付边界与验证

第一批交付两个入口均可浏览的模板、对应源码和指南。实现人员可决定文件命名、组件拆分和具体字段，但不得改变演示/真实 API 的边界，或绕过当前路由、权限和模块契约。上线到公开演示站点是单独的发布步骤，需按现有部署流程验证实际 artifact。

完成时运行与改动直接相关的 `check:route-contract`、`check:import-boundaries`、`check:i18n`、`check:docs`、TypeScript、领域单测、Webpack/Vite 构建及一条完整浏览器流程。测试失败时先修复再扩大验证；记录实际执行命令与结果。若模板加入组件包，另运行组件包契约与 Storybook 检查。

## 已确定的产品选择

用户选择模板在展示应用和企业入口两边默认展示。因此企业入口也包含懒加载的示例模块，但其数据始终只属于当前浏览器会话，与真实企业资源分离。第一批演示申请资源只是通用页面模式的载体，不代表项目面向某一行业。
