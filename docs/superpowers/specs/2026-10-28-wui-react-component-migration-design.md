# WUI React 组件迁移与 6.x 发布设计

## 意图与当前状态

将仍放在 `src/components/stateless` 与 `src/components/stateful` 中、可供其它 React 项目独立使用的实现迁入 `packages/wui-react`，并发布新的 npm 版本。同步把当前组件故事里的 `Pro React Admin 5.0` 展示文案改为 `Pro React Admin 6.0`。

当前两个目录有 143 个直接子目录（139 个 stateless、4 个 stateful）；`wui-react` 已有 12 个公开组件。至少 26 个旧目录直接引用应用内部模块或其它旧组件。仅靠“没有应用 import”也不足以判断可发布：例如 `MusicPlayer` 内置固定的远程演示音频，若干组件依赖应用的 Tailwind 样式，部分 props 仍是隐式 `any`。npm registry 上 `@w.ui/wui-react@6.0.0` 已存在，6.1.0 尚未发布，新增公开组件使用兼容的 6.1.0。仓库已有以 `wui-react-v*` 标签触发、使用 npm Trusted Publishing 的工作流；本机 npm CLI 未登录，不影响该工作流的 OIDC 路径。

## 方案

1. **按发布质量逐个筛选并迁入（已选）**：盘点全部 143 个目录；对可复用组件尽可能完成解耦、props 类型、独立样式和依赖声明，包括编辑器、图表、媒体等重依赖模块。每个保留目录记录具体原因。维持已有 12 个组件的子路径兼容；新增组件按用途分组导出，以满足现有包质量门禁。这个方案覆盖广，但需要改造构建和消费契约。
2. **尽量搬入全部目录**：不区分业务页面与通用组件，连固定项目内容和路由也一并发布。表面覆盖面高，但会把应用功能和演示数据作为公共界面，违反独立消费目标。
3. **先迁少量核心组件**：发布快，但留下其它已经符合条件的组件，与“所有能独立发布的组件”目标不符。

## 迁入判定

对每个目录记录 `migrate`、`adapt then migrate` 或 `keep in app`，并给出证据。迁入需同时满足：

- 运行时代码不引用 `src/app`、`src/platform`、`src/projects`、应用状态/路由/鉴权/反馈服务、私有资产或旧目录路径；相互依赖的可复用组件可一起迁入。
- 组件的内容和行为由 props/children 提供；演示数据、固定远程地址、项目名称及业务文案只保留在 Storybook 故事中。浏览器 API 在渲染时安全，监听器、计时器和媒体资源在卸载时清理。
- 公开 props 有可消费的 TypeScript 类型，交互有可访问名称与键盘行为；包样式能独立工作，不要求消费方额外引入应用 Tailwind 或主题文件。
- 新增运行依赖或 peer 需在 `library-contract.mjs`、包 manifest 与文档中一致声明。编辑器、图表和媒体等重依赖通过分组入口及可选 peer 隔离，消费对应入口时才要求安装该组依赖。
- Webpack/Vite 包构建、严格类型声明、ESM/CJS 独立消费、npm 打包清单、既有文件数与体积预算均通过。若逐组件子路径使全部合格组件超出 250 文件门禁，应重组导出与产物结构，将合格组件放入同一个 6.1.0 版本；不得放宽门禁或静默延后合格组件。

初步扫描有 55 个目录只使用现有包依赖且不直接引用应用模块（54 个 stateless、1 个 stateful）。它们是审核起点而非自动通过清单；另有使用 `motion`、markmap、mermaid、图表、编辑器、视频等依赖的目录，需要根据上述规则改造后单独判断。`CheckableTags` 是 stateful 中的优先候选；`TreeList` 引用旧 `Loading`，可以在两者一起迁入后重新判定。`MusicPlayer` 的固定远程歌曲可移到 Storybook，让公开模块通过 props 接收曲目。`LandingPage`、部署流程等固定产品内容只有在抽成真正通用接口后才可迁入。目录名称不作为迁入依据。

## 实现与兼容

1. 保留 `packages/wui-react` 作为唯一公开包。已有 12 个组件的根命名导出和独立子路径不变。新增实现按 `layout`、`animation`、`data-display`、`forms`、`media`、`visualization`、`editor` 等实际用途放入包源码目录；每组提供一个 ESM/CJS/类型入口并以命名导出提供组内组件。根入口保持轻量，不引入重依赖组。应用 import 改为 `@wui` 源码别名；确需兼容旧内部路径时，只保留薄转发文件，且不把它算作新的实现。
2. 扩展 `config/library-contract.mjs` 的入口描述，使它能同时表示既有默认导出的单组件子路径和新增命名导出的分组子路径。同步更新 Webpack/Vite 构建、最终根入口、包 `exports`、ESM/CJS 消费测试、源码目录验证、依赖契约和包 README。逐组件声明文件保留在组目录内，但不会为每个新组件额外生成一对 JS 子路径文件，从而遵守 250 文件门禁。对 143 个旧目录提供审核清单，说明迁入结果或保留原因。
3. 将本次包版本提升至 `6.1.0`。当前组件故事与包故事中的 `Pro React Admin 5.0` 均更新为 `6.0`；历史兼容范围和依赖版本号不做机械替换。
4. 在本地运行现有完整发布准备（Webpack 与 Vite）、Storybook 类型/构建、应用类型与构建、相关组件行为检查和 `npm pack --dry-run`。发布内容以固定版本和最终通过门禁的源码为准。
5. 将发布源码提交到可追溯的 Git ref，触发 `wui-react-v6.1.0` 可信发布工作流，检查工作流及 npm registry 中的版本、dist-tag 和包入口。若当前环境没有 Git 推送权限或可信发布配置失败，保留已验证产物并报告实际阻塞条件，不宣称发布完成。

## 验收

- 当前组件故事中不再出现 `Pro React Admin 5.0`；组件展示为 `Pro React Admin 6.0`。
- 全部 143 个旧目录均有迁入/保留的可复核结论；所有通过迁入判定的实现均在 6.1.0 包内，应用与 Storybook 可继续使用。
- 发布包的 ESM、CJS、类型、样式、根导出及子路径经独立消费验证；现有发布质量门禁保持通过。
- npm registry 可查询到新版本，`latest` 指向该稳定版本，且发布源码与 Git ref 对应。
